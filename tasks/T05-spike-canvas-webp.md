# T05 スパイク: canvas の WebP サイズを比較する

> [!info] 概要
> - 種別: スパイク / ウェーブ: 1
> - 着手の条件(依存): [[T01-scaffold|T01]]
> - このタスクを待つもの: なし
> - 仕様: [[base64-image-plugin-spec#6.3 リサイズと画質の方針(Q7)|仕様書 6.3]]、[[base64-image-plugin-spec#16. 実装前の検証(スパイク)|仕様書 16章]]

## 目的

仕様書 付録 A の値は cwebp での見積もり。実際のブラウザの canvas でどれだけずれるかを確かめ、画質探索の既定値(画質 0.60〜0.92、0.8 倍ずつ縮小)が妥当かを判断する。

## 作業内容

- [x] 静的な HTML ページと Playwright で、写真を長辺(1600 / 1280 / 1024 / 800)× 画質(0.60〜0.92)でエンコードし、サイズを記録する(Chromium・Firefox)
- [x] 同じ条件の cwebp の結果と比べる
- [x] エンコード1回あたりの時間も記録する(1枚の処理時間の見積もりに使う)

## 結果

> [!success] 結論(2026-09-24)
> - 既定値(画質 0.60〜0.92、0.8 倍、`maxEdge` 1600、`minEdge` 480)は**変えない**。仕様書 6.3 と [[T13-encode-search|T13]] は更新していない。
> - [[T13-encode-search|T13]] には、縮小を `createImageBitmap(bitmap, { resizeWidth, resizeHeight, resizeQuality: "high" })`(以下 cibb)にすること、探索を minFirst(`minQuality` を最初に試す二分探索)にすることを勧める。
> - 測定の環境・手順・再現のコード・全データ: [[canvas-webp-encoding]]

### 測定したこと

- ブラウザ: Chromium 153(headless shell = ソフトウェア描画 / new headless = GPU 描画)と Firefox 155。Playwright 1.63.0 で headless で起動した。
- 写真: 付録 A と同じ 5 枚(2400×1600)。リポジトリには入れていない。
- 条件: 長辺 1600 / 1280 / 1024 / 819 / 800 / 655 / 524 × 画質 0.01〜1.00(0.01 刻み)。0.60〜0.92 の 0.02 刻みでは、3 回ずつ時間も測った。
- 手順は本番と同じにした。`createImageBitmap(file, { imageOrientation: "from-image" })` でデコードし、`drawImage` 1 回で縮小し、`toBlob("image/webp", q)` でエンコードする。縮小は T13 が使うと想定した `imageSmoothingEnabled = true` / `imageSmoothingQuality = "high"`。比較のため、`low` / `medium`、段階縮小、cibb も測った。
- cwebp は、付録 A.2 と同じ方法(ImageMagick の Lanczos で縮小 → `cwebp -q`)で測り直し、付録 A.2 の 20 か所すべてと一致することを確かめた。

### 仕様書 6.3 の探索を当てはめた結果

既定値のまま、ページの中で実際に探索した(画質は 0.01 刻み、minFirst)。「長辺 / 画質」と、エンコード回数・合計時間(3 回の中央値。Apple M5 Pro)。根拠レベル: **実測のみ**

| 写真 | 仕様書 6.3(cwebp の見積もり) | Chromium `high`(ソフトウェア / GPU) | Firefox `drawImage` | Firefox cibb | Chromium cibb |
|---|---|---|---|---|---|
| p1 | 1280 / 77 | 1280 / 78(8 回、0.41 秒) | 1280 / 75(8 回、0.45 秒) | 1280 / 77(8 回、0.45 秒) | 1280 / 78 |
| p2 | 1600 / 80 | 1600 / 81・82(7 回、0.48 秒) | 1600 / 81(7 回、0.51 秒) | 1600 / 80(7 回、0.47 秒) | 1600 / 81 |
| p3 | 1024 / 60 | 1024 / 70・72(9 回、0.40〜0.42 秒) | 819 / 75(10 回、0.43 秒) | 1024 / 60(9 回、0.43 秒) | 1024 / 70 |
| p4 | 1024 / 77 | 1280 / 66(8 回、0.46〜0.48 秒) | 1024 / 72(9 回、0.42 秒) | 1024 / 77(9 回、0.43 秒) | 1280 / 66 |
| p5 | 1600 / 92 | 1600 / 92(2 回、0.13〜0.15 秒) | 1600 / 92(2 回、0.13 秒) | 1600 / 91(7 回、0.40 秒) | 1600 / 92 |

- 合計時間の内訳は、デコード 19ms + 縮小 1〜17ms(長辺ごと)+ エンコード(1600px で 1 回 69〜76ms、1280px で 44〜52ms、1024px で 28〜34ms。中央値)。「デコード + 縮小 + 各エンコードの測定値の和」の見積もりと実測の差は、最大 27ms だった。
- 探索の順番を変えた場合のエンコード回数(5 枚の合計、`drawImage` の `high`): 0.60〜0.92 をそのまま二分探索すると 46〜58 回、0.92 を最初に試すと 37〜41 回、minFirst は 34〜36 回。

### 既定値の判断

**変えない。** 根拠レベル: **実測のみ**(判断は測定値と、仕様書の Q7 の方針による)

- `minQuality` 0.60: cibb で縮小すれば、どのブラウザでも 5 枚すべてが 1024px 以上・画質 0.60 以上に収まった。0.50 に下げると p1 が 1600px / 0.55〜0.57 になり、0.70 に上げると Chromium の p4 が 1024px に下がる。どちらを選ぶかは見た目の方針(Q7)の問題で、ブラウザと cwebp のずれ(±数ポイント)は判断を変えるほど大きくない。
- 上限 0.92: 0.95 にしても 5 枚の結果は変わらなかった。Firefox が可逆になる 0.995 から十分に離れている。
- 0.8 倍: 5 枚は 1600〜1024px に収まった(819px になったのは Firefox の `drawImage` の p3 だけ)。minFirst なら、収まらない長辺のコストはエンコード 1 回だけ。
- `maxEdge` 1600 / `minEdge` 480: 変える根拠になるデータは無かった。480px に近づいた写真は無い。

### T13 への申し送り

詳細は [[canvas-webp-encoding#T13 への申し送り]]。

1. 縮小は cibb にする(デコード済みの ImageBitmap から作り、同じ大きさの canvas に 1:1 で描いてから `toBlob`)。Firefox の `drawImage` はエイリアシングが出る。
2. 探索は minFirst(`minQuality` → 0.92 → 0.01 刻みの二分探索)。5 枚では 2〜10 回・0.13〜0.51 秒。
3. 画質は必ず 0.60〜0.92 で明示する(省略・範囲外はブラウザの既定値、0.995 以上は Firefox で可逆)。
4. サイズの判定は `blob.size` のままでよい(Chromium の 482 B を含む)。収まった Blob を保持し、最後にエンコードし直さない。
5. サイズは画質に対して完全には単調でない。単体テストの偽のエンコーダーに逆転を入れるとよい。
